Bugs — Will Cause Incorrect Behavior

1
db.close() called before transaction completes
lib/indexedDB.ts : 43, 79
High
▶

In both getDataFromIndexedDB and updateDataInIndexedDB, db.close() is called inside request.onsuccess — before the transaction has completed. An open IndexedDB transaction holds a lock on the database. Closing the connection while a transaction is still active can abort the write silently with no error thrown.

The fix is to move db.close() into the transaction.oncomplete callback, guaranteeing the write has finished before the connection is released.

// ❌ Current — db closed before put() finishes
request.onsuccess = () => {
  const db = request.result
  const tx = db.transaction([storeName], "readwrite")
  tx.objectStore(storeName).put(data)
  db.close()  // too early
}

// ✅ Fix — close only after the transaction commits
request.onsuccess = () => {
  const db = request.result
  const tx = db.transaction([storeName], "readwrite")
  tx.objectStore(storeName).put(data)
  tx.oncomplete = () => { db.close(); resolve(true) }
}
2
Direct mutation of useState objects
main/page.tsx : 316, 337 · checkin/page.tsx : 123 · phone-checkin/page.tsx : 313
High
▶

State objects are mutated directly without calling their setter functions. React compares object references to decide whether to re-render. Because the reference does not change, the component never re-renders — leaving the progress counter, sync queue, and booking list showing stale data.

// ❌ Current — mutates the object in place, React won't re-render
listTicket.data = []
retrievedData.data = updatedData

// ✅ Fix — always produce new object references
setListTicket({ ...listTicket, data: [] })
setRetrievedData({ ...retrievedData, data: updatedData })
3
Sync only updates result.data[0]
checkin/page.tsx : 127 · phone-checkin/page.tsx : 316
High
▶

After a successful API call, only result.data[0] is applied back to the local IndexedDB booking cache. The API returns the full array of updated bookings — but this code discards everything after the first item. If the auto-sync interval fires with multiple pending entries, only the first booking's checkInHistory is persisted locally.

// ❌ Current — ignores all updated bookings except the first
const updatedItem = result.data[0]
updatedData[index] = updatedItem

// ✅ Fix — loop over every returned booking and apply each
for (const updatedItem of result.data) {
  const i = updatedData.findIndex(b => b._id === updatedItem._id)
  if (i !== -1) updatedData[i] = updatedItem
}
4
adjustSeats reads wrong booking in secondary modal
components/checkin-modal.tsx : 108–119
High
▶

When the showSeatSelection secondary view is active (triggered from the multiple-bookings list), the +/- buttons call the parent-scope adjustSeats function. That function derives its maximum from data.data — the top-level booking prop — instead of currentBooking, which is the booking the user actually selected. The enforcement is therefore against the wrong seat count.

// adjustSeats in the parent scope:
const adjustSeats = (delta: number) => {
  const checkedIn = data.data?.checkInHistory?.reduce(...)  // ← data.data, not currentBooking
  const maxSelectable = (data.data?.seats || 0) - checkedIn   // ← wrong booking
  ...
}

The secondary modal should derive its own max from currentBooking and either pass a local adjustment handler or pass currentBooking to adjustSeats.

app/page.tsx : 95 · app/main/page.tsx : 349–351
High
▶

Login writes the route code with the key "routecode" (lowercase c). Logout tries to remove "routeCode" (uppercase C) along with two other keys ("checkInProgress", "checkedInPassengers") that are never written in the current code. The actual key is never cleaned up.

// Logout (main/page.tsx:349-351)

localStorage.removeItem("checkedInPassengers")   // never set
6
Logout does not clear IndexedDB
app/main/page.tsx : 349–354
High
▶

handleLogout clears a few localStorage keys and navigates to /. It never calls indexedDB.deleteDatabase("checkin"). The next person who picks up the device will see the previous session's full booking list, passenger names, and phone numbers until they successfully log in with a new route code.

For a shared staff device, this is a privacy concern. The clearDB() function already exists in app/page.tsx — it should also be called on logout.

Code Quality

9
600+ lines of commented-out dead code
main/page.tsx : 1–257 · phone-checkin/page.tsx : 1–224 · qr-processor.ts : processQRCode method
Medium
▶

Three files each contain their entire previous version as a comment block. This nearly doubles the apparent size of the codebase, making it difficult to navigate and understand what code is actually running. These files should be deleted — git history preserves the old versions and is the correct tool for reviewing past code.

Affected files and line counts of dead code: main/page.tsx lines 1–257, phone-checkin/page.tsx lines 1–224, qr-processor.ts processQRCode method (~90 lines), and multiple commented-out card blocks in checkin/page.tsx.

10
Auto-sync logic copy-pasted across three pages
main/page.tsx : 309–340 · checkin/page.tsx : 177–208 · phone-checkin/page.tsx : 366–393
Medium
▶

The exact same 32-line setInterval block (read listticket → call API → clear queue → update booking store) is duplicated verbatim in every page. Any bug fix or behavioral change must be applied in three separate places. This is a strong candidate for extraction into a custom hook, e.g. useAutoSync().

11
handleConfirmCheckIn duplicated across pages
checkin/page.tsx : 111–162 · phone-checkin/page.tsx : 301–352
Medium
▶

The check-in confirmation handler (~50 lines) is identical in both pages: find item by ID, build body, push to listticket, call API, update booking store. A single shared function — ideally inside QRProcessor.checkInPassenger which already exists for this purpose — would eliminate the duplication.

12
QRProcessor.checkInPassenger is broken and unused
lib/qr-processor.ts : 321–358
Medium
▶

This method was written to centralise check-in logic but was never wired up. It also has a bug: it calls listticket.push(body) directly, but the IndexedDB record is shaped as { id: 1, data: [] } — it should be listticket.data.push(body). Either fix and adopt this method (eliminating duplication #11), or delete it.

▶

Every page uses useState<any> for its core data. TypeScript types for Booking, CheckInHistory, and VehicleInfo are already defined in types/bookings.type.ts. Using them would have caught bugs #3, #4, and #12 at compile time.

Architecture

16
No shared state — each page reads IndexedDB independently
All page components
Low
▶

Every page component re-reads all three IndexedDB stores from scratch in its own useEffect. There is no reactive layer (React Context, Zustand, or even a shared module-level cache). The UI is only correct because page navigation causes a full remount. If the app ever needs real-time updates within a page — or if two components on the same page needed the same data — this pattern would break.

Recommended approach: a lightweight React Context (BookingContext) that loads once on app start and exposes typed getters and mutation helpers. This would also eliminate the need for every page to duplicate the IndexedDB read/write logic.

17
NEXT_PUBLIC_API has no null check or startup guard
lib/patchDataToAPI.ts · app/page.tsx : 60
Low
▶

If the environment variable is missing or empty, axios.patch(undefined + "/bookings/adm/check-in") will fail with a confusing network error rather than a clear configuration message. A simple check at module load time or in the app layout would surface this immediately during development or a misconfigured deploy.

// Suggested guard in lib/patchDataToAPI.ts
if (!process.env.NEXT_PUBLIC_API) {
  throw new Error("NEXT_PUBLIC_API environment variable is not set")
}
18
Mock data initializes on every production page load
lib/qr-processor.ts : 43–157
Low
▶

QRProcessor.getInstance() is called on every page that uses phone search. The constructor runs initializeMockData() which builds two Map structures containing hardcoded test passengers. This data is never used in production but consumes memory on every app session. The mock data and related dev helpers (generateTestQRCode, getTestPhoneNumbers) should be tree-shaken or moved behind a process.env.NODE_ENV === 'development' guard.

UX Issues

19
alert() used for all login errors
app/page.tsx : 66, 72, 99
Low
▶

Native window.alert() is blocking, cannot be styled, and renders poorly on mobile devices — especially when the app is installed as a PWA in standalone mode. The project already imports Shadcn's useToast hook and has the toast infrastructure wired up. Errors should use that system or an inline error message below the input field.

20
No offline/online status indicator
app/main/page.tsx
Low
▶

The app's core value proposition is offline-first operation, but the UI gives staff no visibility into whether they are currently online, how many check-ins are queued and waiting to sync, or when the last successful sync occurred. A small status bar — e.g. "● Online · Last sync: 3s ago" or "● Offline · 4 pending" — would significantly improve staff confidence during operations.
