Key Features

🎟️

Smart Booking System

Multi-step booking flow with real-time seat availability, point-pair pricing, and automatic expiration cleanup.

📱

LINE LIFF Integration

Deep LINE platform integration via LIFF framework. Users can authenticate with LINE and use the app inside the LINE mobile app.

💳

QR Payment (KBank)

KBank PromptPay QR payment integration with webhook-driven confirmation and payment expiration management.

🔍

QR Code Check-in

Drivers scan passenger profile QR codes to confirm boarding. Time-window validation ensures check-in only opens 30 min before departure.

📍

GPS Location Tracking

Real-time driver location logging, route progress tracking per pickup point, and passenger GPS-tagged check-in records.

🛡️

Role-Based Access

Three isolated user roles (passenger / driver / admin) each with dedicated UI, middleware protection, and tRPC procedure guards.

🔐

Hybrid Authentication

Supabase Auth (Google, email) + LINE Login with cookie-based session coordination and OTP phone verification via AWS SNS.

🚌

Driver Operations Hub

Full driver workflow: duty sessions, vehicle inspection checklists, round assignment lifecycle, and passenger manifest management.

⚙️

Admin Control Panel

Manage routes, rounds, seat pricing, user whitelist, and view dashboard statistics across all entities.

Data Model

The database has 24 tables across 4 functional domains, implemented with Drizzle ORM on PostgreSQL (Supabase).

Domain 1 — User Management

TableKey ColumnsPurpose
users id, supabase_id, role, email, line_user_id, qr_code, phone Unified user record across all auth providers. Role drives UI and permissions.
phoneVerifications user_id, phone, otp_code, expires_at, verified One-time password tokens for phone number verification via AWS SNS.
whitelists user_id, route_id, granted_by, created_at Admin-controlled per-user route access control.

Domain 2 — Transportation

TableKey ColumnsPurpose
routes id, name, departure_location, arrival_location, status Named transportation corridors between two cities.
routePoints route_id, name, sequence, lat, lng, type (pickup/dropoff) Ordered stops along a route with GPS coordinates.
vehicles id, license_plate, capacity, status, driver_id Vehicle registry with capacity and operational status.
driverVehicles driver_id, vehicle_id, assigned_at Maps drivers to their assigned vehicles.

Domain 3 — Bookings & Payments

TableKey ColumnsPurpose
rounds route_id, date, departure_time, total_seats, available_seats, status, price A scheduled trip instance for a route. Drivers are assigned to rounds.
bookings user_id, round_id, seats, pickup_point_id, dropoff_point_id, status Core booking record linking passenger to a round and stop pair.
seatAssignments booking_id, seat_number, passenger_name Individual seat-level tracking within a booking.
payments booking_id, amount, status, qr_code_url, expires_at, paid_at Payment record with KBank QR reference and expiration.
bookingPayment booking_id, payment_id Junction table linking bookings to payments (supports multi-payment scenarios).
pointPairPricing route_id, pickup_point_id, dropoff_point_id, price Dynamic price per pickup↔dropoff pair on a route.

Domain 4 — Driver Operations

TableKey ColumnsPurpose
driverRoundAssignments driver_id, round_id, status (offered→accepted→started→completed) Tracks which driver is assigned to which round and their progress.
passengerCheckIns booking_id, driver_id, scanned_at, driver_lat, driver_lng, status QR scan event with GPS context for each boarded passenger.
driverSessions driver_id, started_at, ended_at, break_started_at Duty period tracking with break logging.
driverLocations driver_id, lat, lng, recorded_at Append-only GPS trail of driver position over time.
vehicleInspections vehicle_id, driver_id, type (pre/post), status, notes, inspected_at Pre-trip and post-trip vehicle condition records.
driverStatus driver_id, status (available/on_duty/on_break/off_duty) Current real-time availability state of a driver.
routeProgress round_id, point_id, status (arrived/departed), recorded_at Per-stop progress events during an active round.

Policy & Security

Authentication & Authorization

🔐
Dual-provider session validation ENFORCED
Every tRPC context creation checks both Supabase JWT and LINE cookie. A request is authenticated only if at least one valid session exists. LINE sessions are validated against line_user_id in the users table before granting access.
🛡️
Role-based procedure guards ENFORCED
protectedProcedure throws UNAUTHORIZED if no session. adminProcedure additionally checks user.role === 'admin' and throws FORBIDDEN. Drivers cannot access admin routes and vice versa.
🔀
Edge middleware route protection ENFORCED
Next.js middleware.ts runs on every protected route at the edge, before any page renders. Unauthenticated users are redirected to the home page. Role mismatch (e.g., passenger accessing /admin/*) triggers role-appropriate redirect.
⏱️
QR code time-window enforcement ENFORCED
Check-in via QR scan is only accepted within 30 minutes before the scheduled round departure. The driver.scanQRCode procedure validates this server-side — client-side state cannot bypass it.

Input Validation

✅
Zod schema on all tRPC inputs ENFORCED
Every tRPC procedure input is validated with a Zod schema before the handler runs. Invalid shape or type throws a structured BAD_REQUEST with field-level error detail. No raw unvalidated data reaches business logic.
🔢
OTP expiration & single-use ENFORCED
Phone OTP codes have a server-set expires_at timestamp and are invalidated after first successful verification. Re-use or expired codes return UNAUTHORIZED. OTP is never returned to the client API response.
💺
Server-side seat concurrency guard ENFORCED
Seat reservation is performed as a database transaction. available_seats is decremented atomically; concurrent over-booking attempts will see the updated count and be rejected before booking is created.

Data Protection

🔑
Service role key — server-only ENFORCED
SUPABASE_SERVICE_ROLE_KEY is never exposed to the client bundle. All privileged DB operations (user creation, admin queries) use the service role exclusively in server-side tRPC handlers and API routes.
🌐
Environment variable segregation ENFORCED
Client-exposed vars are prefixed NEXT_PUBLIC_*. AWS credentials, KBank keys, Supabase service role, and LINE channel secrets never use this prefix and are only available server-side.
📍
GPS data minimisation RECOMMENDED
Driver GPS is logged per check-in event and as a location trail. Consider adding a data retention policy (e.g., purge driverLocations older than 90 days) to reduce PII exposure surface.

Payment Security

🏦
Webhook signature verification RECOMMENDED
The KBank webhook handler at /api/webhook/kbank should verify the incoming request signature (HMAC or KBank-provided token) before updating payment status. Without this, a malicious actor could forge a payment confirmation.
⏳
Payment expiry & seat release ENFORCED
Unpaid bookings expire automatically. The cleanup job (callable via /api/cleanup-expired-bookings or Vercel Cron) sets booking_status = expired, payment_status = expired, and increments available_seats back on the round.
🚫
No card data stored ENFORCED
Payment is entirely QR-based through KBank. The system stores only the QR reference URL and payment status — no card numbers, CVVs, or sensitive financial data ever touch the application database.
