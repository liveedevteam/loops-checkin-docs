Trigger Conditions — When Does Booking Request Activate?

A booking request is triggered when any one of the following conditions is true at the time the user attempts to create a booking.

Condition 1 — Flag

The round has isRequest = true.
Every booking on this round always goes through request mode, regardless of seat availability.

OR

Condition 2 — Minimum Seat Threshold

Remaining seats < requestMinimumSeats.
When the round drops below a configured threshold, new bookings automatically switch to request mode.

OR

Condition 3 — Full Seats

No remaining seats left (maxSeats − seats − tempSeats ≤ 0).
Instead of rejecting the user outright, create a draft booking and queue for admin review.

// Decision logic in createBooking controller
const remaining = round.maxSeats - round.seats - round.tempSeats

const isRequestBooking =
  round.isRequest === true ||
  remaining < round.requestMinimumSeats ||
  remaining <= 0

if (isRequestBooking) {
  // → draftBookings flow
} else {
  // → normal booking flow (unchanged)
}
Note: When condition 2 or 3 fires, the API must return a distinct response code/flag so the FE can show the correct UI state rather than treating it as a generic error.

Key Features

🎛️

Round-level Request Control

Two new fields on the Round model — isRequest (boolean flag) and requestMinimumSeats (threshold) — give admins fine-grained control per round.

📥

Draft Booking Collection

Request bookings are stored in a dedicated draftBookings collection. No seats are held, no QR is generated yet. The collection acts as a pending queue for admin review.

✅

Admin Manual Approval

Admin reviews draft bookings in the back-office and approves or rejects each one. Approval triggers the full booking + payment creation flow atomically.

🔔

Notification on Approval

When admin approves, all approved users receive a LINE push notification containing the payment link. The FE auto-redirects the user to the payment page upon opening.

⚛️

Transaction-safe Conversion

Converting draftBooking → Booking uses a MongoDB session with startTransaction() to guarantee atomicity: seats incremented, booking created, order created, QR generated — all or nothing.

💳

Auto-redirect to Payment (FE)

After admin approves and sends PoC (QR payment link), the FE detects the notification and automatically navigates the user to /payment/:orderNumber without manual navigation.

🧹

Draft Cleanup Policy

A scheduled cron job marks stale draft bookings as expired after a configurable TTL. Expired drafts are not converted and seats are never allocated to them.

🔄

Normal Flow Unchanged

When none of the trigger conditions are met, the existing createBooking flow runs as-is. No regression risk for standard bookings.

System (Cron — Cleanup Policy)
S1

Daily Cleanup Cron

Cron scans draftBookings where status = 0 (pending) and expiredDateTime ≤ now. Marks them as status = 3 (expired). No seats were ever held, so no reconciliation needed.

cron daily
S2

Hard Delete Old Records

After a longer retention window (e.g. 90 days), expired and rejected draft bookings can be permanently deleted to keep the collection lean.

cron weekly

Admin Flow — Review & Promote

Admin (Back-office)
A

Admin sets isPollEnabled = true and creates a pollRound entry with a name, start date, expiry date, and max votes per user. This makes the voting tab visible to users.

PUT /api/map-routes/:id/poll
B

Monitor Proposals & Moderate

Admin can hide or reject inappropriate proposals (status → 3 = hidden). The back-office shows a live-ranked table of proposals by vote count with a progress bar.

C

After Poll Closes — Approve Top Proposals

Admin clicks "อนุมัติและสร้างเส้นทาง" on a winning proposal. System automatically creates a Route document pre-filled from the proposal data. Admin then creates one or more Round documents for this route.

POST /api/route-proposals/:id/approve
D

Open Booking + Notify Voters

Admin adds the new Route to the MapRoute's routes[] and opens the Round (status → 1). The approve API sends LINE push to all users who voted for this proposal.
