Why PWA?

Check-in events often take place in venues (bus terminals, piers, airports) with unreliable Wi-Fi or mobile data. A PWA allows staff to install the app to their home screen, load it instantly from cache, and operate fully offline — syncing to the server whenever connectivity is restored.

PWA Components Overview

📄 Web App Manifest

Tells the browser how to install the app and present it on the home screen: name, icons, theme colors, display mode, and orientation.

public/manifest.json

⚙️ Service Worker

A JavaScript file that runs in the background, intercepts network requests, and serves responses from the Cache API. Enables offline page loads.

public/sw.js

🔌 PWAProvider

React component in the root layout that handles service worker registration via navigator.serviceWorker.register('/sw.js') on client mount.

components/pwa-provider.tsx

🗄️ IndexedDB

Browser-native structured storage used for all booking data. Persists across sessions and works completely offline. Three object stores managed by the app.

lib/indexedDB.ts

Service Worker Lifecycle

📥

1. Install Event

Triggered when the service worker is first registered or when CACHE_NAME changes. Calls caches.open(CACHE_NAME) and pre-caches all listed URLs. The current cache name is loops-checkin-v2.1.

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open("loops-checkin-v2.1")
      .then((cache) => cache.addAll(urlsToCache))
  )
})
🔄

2. Activate Event

After install, the SW takes control of matching pages. Old caches from previous versions can be purged here (not currently implemented — handled by renaming CACHE_NAME on each deployment).

🌐

3. Fetch Event — Cache-First Strategy

Every network request is intercepted. The SW checks the cache first. If a match is found, it's returned immediately (instant, offline). If not found, the request falls through to the network.

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((response) => {
      return response || fetch(event.request)
    })
  )
})

Deployment Note — Cache Versioning

Important: Update CACHE_NAME on every deployment

The service worker uses a static cache name loops-checkin-v2.1. If the app's JavaScript or HTML changes but the cache name stays the same, users will continue to load stale cached files. The deployment protocol is:

  • Increment the version suffix in public/sw.js before each release (e.g. v2.1 → v2.2)
  • The install event will create a new cache; the old one should be purged in the activate event
  • All clients will receive the updated app on their next page load
